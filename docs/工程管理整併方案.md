# 工程管理整併方案：主計畫 × 子計畫 Issue 管理

> 文件類型：工程問題分析（供 harness agent 擴充使用）
> 日期：2026-05-17
> 專案：智慧分案 POC → smart-ai 重構

---

## 一、緣起

本專案初期以單一 `PLAN.md` 管理所有計畫，隨著功能增加，陸續拆出多份細節文件：

```
PLAN.md                          ← 路線圖
input/smart-ai-plan.md           ← 詳細規格
input/smart-ai/phase-A-*.md      ← Phase A 工作清單
input/smart-ai/phase-B-*.md      ← Phase B 工作清單
input/smart-ai/phase-C-*.md      ← Phase C 工作清單
input/smart-ai/deferred.md       ← 暫緩項目
status.md                        ← 當前進度
```

這個結構在初期合理，但當工項數量增加後，開始出現管理摩擦。

---

## 二、要解決的問題

### 2.1 狀態分散，雙重維護

工項狀態（checkbox）存在 phase 細節檔中，但 `status.md` 同時以文字描述相同進度。完成一個工項需要更新兩個地方，漏改其中一處就產生不一致。

**實際發生案例**：Phase A 的工項在 `phase-A` 檔使用 A1~A6 編號，`status.md` 使用 A.1~A.4 編號（合併了幾個步驟），導致 session 啟動時需要人工對照轉換，還是對應錯誤。

### 2.2 無依賴關係記錄

現有 phase 檔為線性清單，沒有明確記錄哪個工項依賴哪個。Agent 或開發者無法快速判斷「A4 沒完成，B1 不能動」。

### 2.3 取消 / 暫緩無統一處理

取消項目（如 A5 lora 空目錄）原先散在 `deferred.md` 的敘述段落，難以與主工項清單對照。刪掉後沒有歷史記錄；保留後出現在主流程容易造成混淆。

### 2.4 無法一眼看全局

看完整 backlog 需要打開 phase-A、phase-B、phase-C 三個檔案。跨 Phase 的依賴（如 B1 依賴 A6 完成）在各自的檔案中隱式提及，沒有集中呈現。

---

## 三、工程面的方法

### 3.1 核心原則：單一 Source of Truth

參考 GitHub Issues / Linear 的設計：**每個工項只有一個地方記錄狀態。**

### 3.2 角色重新定義

| 檔案 | 原角色 | 新角色 |
|------|--------|--------|
| `PLAN.md` | 主計畫（持續更新） | 初版計畫存檔（不再更新工項細節） |
| `input/smart-ai-plan.md` | 規格文件 | 同上，初版規格存檔 |
| `input/backlog.md` | 不存在 | **唯一工項狀態來源**（新增） |
| `input/smart-ai/phase-*.md` | 工作清單（有 checkbox） | 規格說明（無 checkbox，狀態指向 backlog） |
| `input/smart-ai/deferred.md` | 暫緩描述 | 暫緩說明（backlog 中用 ⏸ ID 對應） |
| `status.md` | 進度描述 + checkbox 鏡像 | 精簡指針：「當前工項 ID + 下一步指令」 |

### 3.3 backlog.md 格式設計

```markdown
| ID | 說明 | 狀態 | 依賴 | 完成日 |
|----|------|------|------|--------|
| A4 | 建立目錄樹 | ⬜ | A3 | — |
| A5 | ~~預留 lora 空目錄~~ | 🚫 | — | — |
| B1 | api/main.py | ⬜ | A6 | — |
```

狀態碼：`⬜ 待完成` / `🔨 進行中` / `✅ 完成` / `🚫 取消` / `⏸ 暫緩`

- **取消項目**用刪除線 + 🚫 保留歷史，不刪除
- **依賴欄**記錄阻擋項目的 ID，Agent 可直接判斷是否可以開工
- **新增工項**：給定唯一 ID、填依賴、在對應 phase 細節檔補驗收條件

### 3.4 status.md 精簡方向

```markdown
## 當前工項
🔨 **A4** — 建立 systems/chiefmail_back/orgs/hpa/ 目錄樹

## 下一步指令
1. 過 /karpathy-guidelines
2. 建立目錄樹（含 .gitkeep）
3. 驗收：目錄結構符合 backlog.md A4 規格
```

移除：進行中任務 checkbox 列表（已移至 backlog）、已完成 checkpoint 的重複描述（git log 有）。

## 四、Harness 需要異動的檔案

以下是採用新結構後，Harness 框架中需要更新的位置：

### CLAUDE.md

1. **子文件地圖**：加入 `input/backlog.md`（工項追蹤）一列
2. **Session 啟動 SOP**：步驟一改為「讀 `status.md` → 找當前工項 ID → 查 `input/backlog.md` 確認依賴」
3. **重要規則**：加入「工項狀態只改 `backlog.md`，不改 phase 細節檔」

### status.md

1. 移除「進行中任務」checkbox 清單
2. 改為「當前工項 ID」指針格式
3. 已完成 checkpoint 保留最近一條，其餘移至 `status-history/`

### learnings.md

新增一條教訓：

```
[2026-05-17] 工項狀態分散在多個 phase 檔 + status.md
→ 編號錯位，完成一項需改兩個地方
→ 根因：沒有單一 source of truth
→ 規避規則：工項狀態集中在 input/backlog.md，phase 檔只存規格說明
```

## 五、導入後的檔案結構

```
input/
├── backlog.md               ← 唯一工項狀態（新增）
├── smart-ai-plan.md         ← 初版規格存檔
└── smart-ai/
    ├── phase-A-架構分機關.md ← 規格說明（無 checkbox）
    ├── phase-B-API.md        ← 規格說明（無 checkbox）
    ├── phase-C-排程.md       ← 規格說明（無 checkbox）
    └── deferred.md           ← 暫緩說明（對應 backlog D 系列 ID）
```

## 六、新增計畫的流程（未來擴充）

1. 新功能提案寫入 `input/` 子計畫檔（提案階段）
2. 使用者審查後，在 `input/backlog.md` 加入新 Phase / 新 ID
3. 不自動寫入 `PLAN.md`（PLAN.md 是存檔，不是活文件）
4. `status.md` 更新指針到新工項 ID
